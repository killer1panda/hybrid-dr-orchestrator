## Phase 0: Planning, Specifications & Architecture Decisions
- **What was built:** Architecture specification (RTO $\le$ 15m, RPO $\le$ 5m budget), four accepted Architecture Decision Records ([ADR-001](file:///Users/ajay/Downloads/hybrid-dr-orchestrator/docs/decisions/0001-onprem-platform.md) through [ADR-004](file:///Users/ajay/Downloads/hybrid-dr-orchestrator/docs/decisions/0004-dns-and-healthchecks.md)), cost model (~$0.93/mo standing, ~$0.12/drill), and risk register with mitigation strategies.
- **Why this design:** Pilot Light pattern provides the optimal trade-off between strict durability (continuous WAL streaming keeps RPO < 60s) and minimal cost (zero standing EC2 compute in AWS, provisioning replica on-demand via Terraform/Ansible). Dual-mode orchestrator prevents shared failure domains.
- **Limits and trade-offs:** On-demand provisioning in AWS introduces 3.5 minutes of EC2/VPC boot latency into the RTO budget compared to a Warm Standby (which has RTO < 3m but costs $35+/mo). Residential NAT requires push heartbeats and API-driven Route 53 updates rather than external pull probes.

## Phase 1: On-Premises 3-Tier Lab & Ground-Truth RPO Probe
- **What was built:** A containerized on-premises 3-tier lab environment (Nginx reverse proxy at 192.168.10.10, FastAPI backend at 192.168.10.20, PostgreSQL 16 with WAL archiving at 192.168.10.30, and a 1-second monotonic RPO probe daemon at 192.168.10.25) running on a dedicated bridge network (`dr_onprem_bridge`, 192.168.10.0/24) with a formal chaos allow-list (`lab-inventory.yml`).
- **Why this design:** Lightweight, deterministic local simulation that requires zero cloud spend while preserving real network topology semantics (static IPs, reverse proxy buffering, database health checking, read-only fencing detection, and WAL archiving to volume). The separate RPO probe inserts timestamped sequence IDs every second to provide unforgeable ground-truth data loss metrics during disaster drills.
- **Limits and trade-offs:** Docker bridge networking does not fully simulate hypervisor-level physical fault domains (such as power supply failures or kernel panics), and storage writes share the host OS disk subsystem. In enterprise environments, this would be deployed on dedicated Proxmox VE / KVM hypervisors with out-of-band IPMI fencing (STONITH).

## Phase 2: Persistent AWS Foundation & IAM Least Privilege
- **What was built:** Persistent AWS foundation in `ap-southeast-2` (Sydney) with modular Terraform: SSE-S3 encrypted backup bucket with versioning and lifecycle rules (`s3-backup`), least-privilege IAM roles and user (`iam-roles`), private Route 53 hosted zone (`dr-lab.internal`), SSM fencing parameter (`/hybrid-dr/active-site`), AWS Budget alarm ceiling ($15.00/mo) with SNS notifications, and cost audit script (`scripts/cost_guard.sh`).
- **Why this design:** Standing cost optimized to ~$0.93/month by leveraging SSE-S3 (avoiding $1.00/mo customer-managed KMS key) and Terraform native S3 backend locking via `use_lockfile = true` (avoiding DynamoDB state-locking tables). Negative security testing is built in: `dr-onprem-backup-writer` has an explicit `Deny` on `s3:DeleteObject` to protect against ransomware or accidental deletion of database backups.
- **Limits and trade-offs:** Scoped IAM user credentials for on-premises backup shipping require periodic rotation procedures rather than IAM Roles Anywhere with x509 PKI certificates, which was deferred to avoid the $400/mo AWS Private CA fee or running a self-hosted PKI. Route 53 private hosted zone has a fixed $0.50/month fee regardless of query volume.

## Phase 3: Hybrid Network, WAL Shipping & Automated PITR
- **What was built:** End-to-end continuous hybrid data replication pipeline: zero-leak WireGuard VPN templates with NAT traversal (`PersistentKeepalive = 25`), continuous PostgreSQL WAL shipper (`scripts/archive_wal.sh` with gzip compression directly into S3), full snapshot backup streamer (`scripts/backup_base.sh` streaming `pg_basebackup` directly into S3), automated point-in-time recovery test harness (`scripts/test_restore.sh`), 30-second hybrid heartbeat daemon (`scripts/heartbeat_publisher.py` writing to SSM Parameter `/hybrid-dr/heartbeat/onprem` and CloudWatch), and complete operational runbooks (`docs/runbook.md`).
- **Why this design:** Continuous WAL archiving decouples replication frequency from snapshot size, allowing us to hit our target RPO <= 60 seconds without running an expensive warm standby replica database. Packaging backups with gzip and streaming directly to S3 avoids local disk exhaustion. The automated restore harness verifies backup integrity on every run, asserting both table counts and the precise timestamp age of the monotonic RPO probe.
- **Limits and trade-offs:** WAL shipping provides asynchronous replication with a delay equal to the segment size or `archive_timeout` (60s), meaning in an abrupt catastrophic site destruction up to 60s of writes could theoretically be lost (within our 5-minute RPO budget). In synchronous streaming replication (e.g. pgpool or physical standby), RPO would be 0s, but that requires standing compute in AWS and introduces latency penalties on on-prem transaction commits across the WAN.

## Phase 4: Ephemeral AWS Replica & S3 Encrypted PITR
- **What was built:** An on-demand, ephemeral AWS DR replica stack provisioned via Terraform (`infra/aws/envs/dr`) and configured via Ansible (`ansible/playbooks/site.yml`, `restore_db.yml`, `smoke_tests.yml`). The stack includes dynamic ingress detection (restricting SSH strictly to the orchestrator operator's `/32` IP), client-side PBKDF2 AES-256 decryption of base backups from S3, automated WAL replay to PostgreSQL read/write promotion in Docker (`network_mode: host` to access IMDS), smoke testing of FastAPI (`/healthz` and write validation `POST /items`), unforgeable RPO measurement from continuous sequence probes, and clean teardown via `make dr-down`.
- **Why this design:** Pilot Light pattern with zero standing EC2 compute delivers dramatic cost savings ($0.00/mo standing vs. $35+/mo for always-on replica). Keeping persistent resources (S3 bucket, Route 53 zone, IAM, budgets) in a decoupled Terraform root guarantees that ephemeral teardown can never wipe backups or state locks. S3 native state locking (`use_lockfile = true`) avoids DynamoDB table costs.
- **Limits and trade-offs:** Cold provisioning introduces ~14 minutes of package installation and image building (`apt`, `docker`, `pip`) on a stock Ubuntu AMI, yielding a total cold failover RTO of ~21 minutes. In enterprise production, this latency is eliminated by using Packer to pre-bake Golden AMIs with container images pre-cached, dropping RTO to under 7 minutes while maintaining zero standing EC2 compute spend.

## Phase 5: Python State Machine & Quorum Consensus Engine
- **What was built:** A Python 3.11 disaster recovery orchestrator with strict static typing (`mypy --strict`), structured monotonic JSONL auditing, an explicit deterministic state machine (`IDLE -> FENCING -> PROVISIONING -> RESTORING -> TESTING -> CUTOVER -> COMPLETED`), a multi-signal quorum engine requiring agreement across independent fault domains (HTTP, TCP, push heartbeats) before declaring disaster, atomic state persistence (`os.replace`), leader locking via non-blocking file locks, safe subprocess execution wrappers (`shell=False`, timeouts, output capture), and a CLI supporting `--dry-run` drills.
- **Why this design:** Dual-signal failure domain correlation prevents devastating false-alarm failovers caused by single-probe anomalies (e.g. proxy restarts or transient connection resets). The state machine is pure and decoupled from side effects via typing `Protocol` interfaces, enabling exhaustive unit testing without hitting real cloud providers. Atomic state persistence guarantees crash resilience: if the orchestrator process dies mid-failover, restarting it immediately resumes from the exact recorded transition state without repeating completed steps.
- **Limits and trade-offs:** The file-based leader lock provides local mutual exclusion for a single host or mounted distributed filesystem; in a fully geographically distributed multi-witness control plane, a distributed consensus store (e.g. AWS DynamoDB conditional writes, etcd, or Consul) would be required to prevent split-brain leader elections across disparate networks.

## Phase 6: Guarded Chaos Drills, Benchmarking & Reverse Failback
- **What was built:** Guarded chaos injection tooling (`scripts/chaos_kill_onprem.sh`, `scripts/chaos_network_drop.sh`) strictly restricted to `lab-inventory.yml` allow-lists with negative target and host interface guards (`en0`, `lo`); an end-to-end automated drill runner (`scripts/drill.sh`) benchmarked across three failure scenarios (clean catastrophic outage, stale client DNS cache propagation window, and mid-failover orchestrator crash with atomic recovery); and an automated reverse replication failback playbook (`ansible/playbooks/failback.yml`) syncing delta changes via encrypted SSH tunnel, verifying database row counts and probe continuity, restoring Route 53 DNS and SSM fencing to `onprem`, and cleanly tearing down AWS ephemeral compute (`make dr-down`).
- **Why this design:** Disaster recovery is only half an architecture without automated failback and chaos resilience testing. Restricting chaos tooling strictly to lab container inventories and requiring explicit `--confirm` protects the operator's host operating system and network. Performing reverse delta synchronization prior to DNS rollback and AWS teardown guarantees zero data loss for post-failover writes. The failback playbook includes a hard abort guard: if database delta verification fails, it refuses to touch Route 53 or destroy the AWS replica, preventing split-brain or data corruption.
- **Limits and trade-offs:** Reverse delta synchronization relies on a `pg_dump` export over an SSH tunnel, requiring a brief write freeze (<5s) on the AWS replica during final cutover. In large-scale enterprise environments with high transaction throughput (thousands of writes per second), this would be replaced with continuous bidirectional logical replication (PostgreSQL logical replication slots) to achieve continuous two-way synchronization without any write freeze. Additionally, client DNS caching remains constrained by resolver compliance with the Route 53 60-second TTL.

## Phase 7: Observability as Code, CI/CD Pipeline & Security Hardening
- **What was built:** Production observability stack as code (Prometheus v2.50, Blackbox Exporter v0.25, Alertmanager v0.27, Grafana v10.4 with provisioned `hybrid-dr.json` dashboard) monitoring multi-signal quorum metrics, HTTP/TCP/database probes, and backup freshness; a hardened GitHub Actions CI pipeline (`.github/workflows/ci.yml`) pinning all actions to immutable full commit SHAs, enforcing Dependabot automated dependency security updates, and using GitHub OIDC with a strictly read-only AWS IAM role (`dr-github-actions-readonly`) that forbids `terraform apply` from CI; and a comprehensive security audit in `docs/security.md` featuring a STRIDE threat model, complete secrets inventory, IAM least-privilege matrix, empirical S3 public access block verification, and time-boxed finding waivers.
- **Why this design:** Observability as Code ensures monitoring infrastructure is versioned and reproducible alongside production workloads without click-ops. Provisioning Grafana dashboards and Prometheus alerting rules in Git guarantees that alerts fire reliably across environments. In CI/CD, strictly prohibiting `terraform apply` from automated workflows prevents accidental cloud mutations, state drift, or unapproved spending, while GitHub OIDC eliminates long-lived static AWS access keys in repository secrets. S3 public access block (all 4 flags active) and IAM policies with explicit `Deny` on `s3:DeleteObject` create an immutable, ransomware-resistant backup archive.
- **Limits and trade-offs:** The local Prometheus/Grafana stack monitors the on-premises site and Blackbox endpoints locally via Docker Compose; in an active failover drill where the on-prem host is powered off, local monitoring becomes unavailable, shifting real-time monitoring to AWS CloudWatch metric filters and SNS topic alarms (`dr-budget-spend-alerts`). Additionally, while GitHub OIDC prevents static key exposure, full pull-request speculative planning requires configuring a public OIDC identity provider in the target AWS account.

## Phase 9: Cloud-Native Evolution, Property Fuzzing & CDC Replication
- **What was built:** Production AWS Step Functions State Machine defined as code via Amazon States Language (ASL JSON) and packaged into a modular Terraform module (`infra/aws/modules/step-functions`); an offline Python ASL syntax validator and deterministic execution simulator (`hybrid_dr.step_functions.StepFunctionsSimulator`); a decoupled Terraform CLI automation runner (`hybrid_dr.actions.TerraformRunner`) providing structured I/O and dry-run safety; property-based invariant fuzz testing using `hypothesis` (`tests/test_properties.py`) mathematically proving four core invariants (single-signal fault tolerance, maintenance mode failover suppression, flapping dampening, and crash recovery determinism); and a continuous PostgreSQL logical replication (CDC) stream harness (`infra/onprem/cdc/` and `scripts/test_logical_cdc.sh`) verifying real-time change data capture through replication slots with zero standing cloud compute spend (\$0.00).
- **Why this design:** Transitioning orchestrator definitions to native AWS Step Functions ASL allows production enterprises to leverage serverless, managed distributed state orchestration with native retry backoffs and Dead-Letter routing without maintaining a custom orchestrator VM. The offline Python simulator enables 100% test coverage and validation during CI and local drills without paying AWS Lambda/Step Functions execution fees. Property-based fuzz testing with Hypothesis pressure-tests the Quorum Engine against thousands of randomly generated signal failure permutations to prove that no single-class failure can ever trigger an accidental failover. The logical replication harness demonstrates how modern architectures achieve sub-second RPO streaming compared to 60-second batch WAL archiving while strictly honoring our \$0.00 standing compute FinOps constraint.
- **Limits and trade-offs:** Logical replication requires maintaining active replication slots on the primary database, which will retain WAL on disk if the subscriber or CDC consumer disconnects for extended periods; in production, this requires monitoring `pg_replication_slots.active` and setting `max_slot_wal_keep_size`. While the ASL state machine is fully validated and ready for production deployment, live execution of the Step Functions workflow in AWS was kept optional to maintain absolute zero standing cloud compute spend.
